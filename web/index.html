Zcash quantum exposure survey

How much ZEC would survive Q-Day?

A large enough quantum computer breaks the discrete-log assumptions under every pool Zcash uses today. Shorline replays the chain from genesis and sorts every zatoshi by what such an adversary could do to it, following the threat model in ZIP 2005 and the scope of ZIP 2007.

Verified to the zatoshi

Shorline doesn't trust an explorer's address balances. It streams every block from public lightwalletd servers, replays every transparent input and output in order, and rebuilds the UTXO set itself. That total is then compared with the transparent value pool a Zebra node reports for the same block. If a single spend were mis-attributed, the totals would not match.

Exposure is still growing

Funds sent to an address whose key is already public are exposed the moment they arrive. Most of this is exchange and pool hot-wallet reuse. Wallets that follow ZIP 315 never reuse transparent addresses.

Answering the ZIP 2007 survey question

zcash/zips#1302

The ZIP 2007 discussion (#1302) lists as a next step: "Survey the chain to see what proportion of funds are currently recoverable and in each category." It also asks whether P2SH-wrapped P2PKH or P2PK redeem scripts are used at all. Shorline fetched the first spend of every funded P2SH address whose script has been revealed and classified the redeem script.

Hidden on Zcash, exposed on Ycash

cross-chain

In July 2019 Ycash forked from Zcash at block 570,000 and copied every balance, keys included. When someone spent their Ycash airdrop, the spend published the same public key that guards their ZEC. Shorline asked a Ycash server about the largest addresses that look hash-protected on Zcash and were funded before the fork. It then checked each Ycash spend's scriptSig for a key whose Hash160 matches. A match proves the key is public.

Check an address

Paste a transparent address (t1…, t3… or tex1…). The lookup runs in your browser. It downloads one shard file covering every funded address that shares the address's first two characters after the prefix, so this site never learns which address you checked.

Stick a tag on a hardware-wallet box, a paper backup or an exchange deposit card. Tapping it with a phone opens this checker with the address filled in. The tag holds only a public address link, never a key, and the address sits after the # so it never reaches any server.

For a live answer straight from the chain, run shorline check <address>.

What to do about it

Holding transparent ZEC

Move it to a fresh Ironwood shielded address in a ZIP 2005-compliant wallet. Ironwood notes are designed to be recoverable through a future post-quantum Recovery Protocol. Sweep each address completely so no change is left behind a revealed key.

Holding Sapling, Orchard or Sprout

Migrate to Ironwood. ZIP 2005 is explicit: funds left in these pools would be inaccessible once their protocols are disabled. Use a wallet that follows ZIP 318, which splits the move into standard denominations so the public amount crossing the turnstile doesn't fingerprint you.

Running a multisig or treasury

Transparent P2SH multisigs reveal every key on first spend. Their recovery is the hardest case in ZIP 2007. Re-create the treasury as a FROST threshold key (ZIP 312) in the Ironwood pool, which ZIP 2005 explicitly supports.

Method

StreamEvery block from genesis via GetBlockRange with poolTypes = [TRANSPARENT] from public lightwalletd servers (zec.rocks). Nothing is stored on disk.
ReplayA Rust engine applies every input and output in order, tracking each address's balance and the height its public key or redeem script was first revealed.
ClassifyEach output falls into a ZIP 2007 category: P2PKH hidden or exposed, P2SH unseen or seen, P2PK, or bare multisig. A P2PK or multisig output also exposes the matching t1 address, in both key encodings.
VerifyThe reconstructed transparent total is checked against Zebra's valuePools at the same height. Shielded pools come from the same snapshot.
An adversary can … break Spend authentication for the transparent pool by forging ECDSA-over-secp256k1 signatures used in scripts, provided that the public key has been revealed (i.e. if the address has been spent from previously …).ZIP 2005, Threat model
Recovery would not be possible for funds still in the Sprout, Sapling, or Orchard pools; all such funds would be inaccessible after their respective protocols are disabled.ZIP 2005, Abstract

Limits, stated plainly

  • Exposed is a lower bound. Keys can also leak off-chain: shared xpubs, signed messages, or spends of the same coins on the 2019 Ycash fork. None of that is visible here.
  • Hash-protected is an upper bound, for the same reason. It is also only recoverable in principle: it needs the ZIP 2007 circuit to be built and deployed.
  • Unseen P2SH cannot be classified from public data, as #1302 notes. Their scripts appear only when spent.
  • Shielded privacy is a separate risk. A quantum adversary who knows a shielded address could decrypt notes sent to it. That depends on which addresses have been published, not on the chain, so it isn't measured here.
  • This is not a prediction of when, or whether, a cryptographically relevant quantum computer will exist.
